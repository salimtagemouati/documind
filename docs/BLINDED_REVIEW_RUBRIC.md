# Blinded human-review rubric

## Prepare and blind

Use at least two independent reviewers; do not show them provider names, model IDs, model-specific latency, tokens, cost, run order or the private mapping. Generate a randomized packet and a private mapping from a completed run:

```bash
backend/.venv/bin/python scripts/blind_model_reviews.py export eval/runs/dev-pilot-live/results.json /private/path/reviewer-packet.json /private/path/private-mapping.json
```

Give reviewers separate copies of the packet, not the mapping, raw results, logs or report. Blind IDs are randomly generated per response, then shuffled. Packet content includes the question, exact supplied context, answer, gold answer and gold page references so reviewers can adjudicate; it omits provider and model metadata. Partial answers are labeled partial, but errors and in-flight attempts are excluded. Answers themselves can disclose identity or style, so perfect blinding is not guaranteed; note suspected identity exposure rather than changing the answer. Keep mapping and all outputs private, and avoid sharing account data. A reviewer must not modify question, evidence, answer, or blind ID; the importer checks these fields against hashes in the private mapping.

Inspect evidence as supplied, including its exact source order, not evidence that the model did not receive. Check the full source page and gold reference separately if a retrieved chunk omits it. A gold label is a proposed human-authored reference, not proof: mark an ambiguous or incorrect label for adjudication. This pilot uses curated page contexts; none were generated by a model or production pgvector retrieval.

## Score each response

1. **Correctness (`correctness_human`):** `true` only when the response answers the question correctly and completely, including numbers, units, conditions and conflicts, without materially false claims. `false` for material wrongness, incompleteness, or failure to answer an answerable question. Use `null` if a label, question or model response is genuinely ambiguous, truncated, or the decision requires external facts. For an unanswerable question, a correct abstention can be marked true. Record relevant rationale in claim notes or the reviewed packet.
2. **Abstention (`abstention_correct_human`):** judge the actual response, not a keyword matcher. Set `true` for an appropriate evidence-limited refusal when evidence is absent, or an appropriate non-refusal when answerable; `false` for hallucinating in the absence of evidence or refusing despite sufficient supplied evidence; `null` for partial/refusal ambiguity, missing relevant retrieval or an unresolved gold label. Report negative-case correct refusals and answerable-case false refusals separately; do not treat the four v1 negatives as a reliable population estimate. A conflicting-document case should state the conflict and uncertainty, not choose a winner without evidence.
3. **Atomic claim support (`claim_review`):** split the answer into individual verifiable claims. For each enter `{"claim":"...", "supported":true|false|null, "citation_supported":true|false|null, "notes":"..."}`. `supported=true` means the supplied context entails the claim, including qualifiers and calculations; `false` means unsupported or contradicted, `null` means undecidable. A mathematical conclusion may be supported by multiple cited premises. A correct-looking conclusion based only on external knowledge is unsupported. Do not grade factual support by word overlap.
4. **Citation accuracy (`citation_supported`):** for each claim determine whether the cited number maps to the exact supplied source and any page number matches, then whether the cited passage actually entails the claim. A reference-valid number alone is insufficient. Mark `false` for missing, fabricated, wrong-page, misattributed or irrelevant references when a citation is required; use `null` for claims requiring no citation or ambiguous cases. References to a fabricated citation *as data* are not endorsements; the current automated validator may nonetheless reject them. Record the distinction in notes. The display's source list can include uncited chunks.

For a partial response, record the visible claims but leave overall correctness and abstention judgments `null` unless the review protocol explicitly changes. Provider errors, no response and ambiguous in-flight requests are not negative model answers; report them separately. If retrieval omitted a gold page, record retrieval failure separately from generation faithfulness. Do not silently repair the held-out label or inferred context.

## Reconcile and report

Compare independent reviews without revealing model identity. Adjudicate disagreements and document unresolved cases. Use exact numerators/denominators for answerable correctness, negative-case correct refusals, answerable false refusals, claim support and citation support; report `null`/unreviewed and provider errors. The pilot is 12 questions and one repetition per model, far too small for reliable model ranking or p95 claims.

Once adjudicated, convert a reviewed packet with the private mapping:

```bash
backend/.venv/bin/python scripts/blind_model_reviews.py import /private/path/adjudicated-packet.json /private/path/private-mapping.json /private/path/importable-reviews.json
```

The importer refuses unknown, duplicate, missing or tampered items and never overwrites existing outputs. Apply the imported file through `evaluate_models.py` with the original run options plus `--resume --report-only --reviews /private/path/importable-reviews.json`. Report-only does not dispatch calls. Both the answer key and original v1 labels remain unchanged.
