## Runner controls and residual risk

- All models receive the same question, ordered source content, system instruction and output limit per case. Model-specific wire formats differ. Gemini uses provider-default temperature/thinking and Groq uses temperature 0.1 and default reasoning; they are not identical decoding regimes. Groq documents GPT-OSS default reasoning effort as medium. `--max-output-tokens` maps to Google's `maxOutputTokens` and Groq's `max_completion_tokens`. A 512-token cap can truncate reasoning and visible output; use the pilot's 2,048 setting and report actual finish reasons. Equal caps do not imply equal reasoning budgets or comparable visible output.
- Model IDs and request shapes match public documentation: [Google model card](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite), [Google generateContent REST](https://ai.google.dev/api/generate-content), [Groq model catalog](https://console.groq.com/docs/models), [Groq chat API](https://console.groq.com/docs/api-reference), [Groq reasoning](https://console.groq.com/docs/reasoning). Documentation lists the models; it does not prove current account access, availability, actual response fields, quotas or latency. A live compatibility smoke test itself requires explicit authorization and counts toward the request/spend budget.
- The journal persists the reservation and `started` state before dispatch. One HTTP client call is made with transport retries disabled and no fallback. Error, timeout, HTTP status, finish reason, token counts and partial output are now recorded; a token-limit finish is `partial`, not `completed`. Errors and ambiguous `started` rows are never automatically replayed. Provider-side processing may still be billable after timeouts. `--resume` refuses changes to code, dataset, context hashes or run settings. Locks and deduplication apply **only inside one output directory**: rerunning into another directory can duplicate paid calls. Do not treat the journal as a global idempotency guarantee.
- Maximum requests and a summed reservation are checked before dispatch. When reported token usage implies a higher cost, the runner now raises the retained reservation before considering another request; it never releases reservations. The input bound is a UTF-8-byte heuristic and rates are bundled estimates; no proof establishes it as a provider-side or absolute billing ceiling, and provider-managed charges may exceed it. Use provider-side spend controls, verified prices and a deliberately small approved budget. Actual billed amounts remain unknown without reconciliation. Empty or malformed provider payloads can still lack usage. Partial and error rates must be reported with explicit denominators; do not infer completion from a reference-valid partial answer.
- The current dry-run check validates our local request shapes, not provider compatibility. Imported end-to-end context metadata now records source execution (`mock`/`live`) and retrieval method; SQLite synthetic retrieval is clearly labeled and is neither model-generated text nor production pgvector/HNSW. No reranking executes in this harness, and `skipped` is reported. If end-to-end synthetic SQLite retrieval misses a gold page, the expected document-level answer may not be answerable from the supplied context; grade retrieval and generation separately. The selected pilot avoids that ambiguity by using frozen curated pages.
- Generated `results.json`, CSV and raw review templates include provider/model identity. They are **not blinded**. `scripts/blind_model_reviews.py` creates a shuffled response packet with random IDs and a separate private mapping; response text can still reveal model identity. Follow `BLINDED_REVIEW_RUBRIC.md`, use independent reviewers and adjudicate disagreements before unblinding. A reference-valid citation is not semantic support.
