# Model benchmark protocol

Version `documind-synthetic-v1`: 64 individually authored cases over eight fictional documents, with four development and four held-out documents (32 cases per split). SHA-256 is stored beside the dataset. Each case includes an expected answer or abstention and supporting document/page labels. These are synthetic author labels; **independent human review has not yet been performed**. Gold was not derived from model answers. Do not tune prompts, retrieval or graders on held-out results; revise and freeze a new dataset version if changes are needed. The small repetitive corpus is a starting diagnostic, not the 100-case, 20-document evaluation target.

Held-out mix: 10 direct, 8 numeric, 6 multi-hop, 4 unanswerable, and one each of cross-document, contradictory, misleading-citation and prompt-injection cases. Development has 13 direct, 6 numeric, 5 multi-hop, 4 unanswerable and one each of those four challenge categories. All questions are individually specified, but the synthetic documents and labels have not been reviewed by a separate independent annotator. Four negative cases are too few to infer a reliable refusal rate. Some contexts are deliberately broad; cross-document document selection and frozen curated contexts are oracle-like and should not be mistaken for retrieval performance.

## Two measurements

1. **End-to-end diagnostic:** synthetic page texts enter the existing chunker (800/100), disposable SQLite index and application lexical retrieval. Candidate selection and disabled reranking are identical for all models. The output records retrieval timing and `rerank_status=skipped`. It is not production pgvector/HNSW, embedding generation, file parsing, billing, authentication, or a full API deployment. Implement and evaluate a separate disposable PostgreSQL/pgvector pipeline with cost-accounted embedding calls before making production retrieval claims.
2. **Generation-only:** use the end-to-end result's frozen contexts via `--contexts-from`. Its dataset hash, source IDs, pages, chunk contents and per-model context hashes are checked before use. The same prompt and exact context go to all models; retrieval is not repeated per provider. Without that option, generation mode uses manually curated frozen pages, not retrieved results. Ground-truth answers and supporting labels never go into provider prompts.

Use the same fixed request/output budget, timeout and evidence. The schedule is deterministically shuffled by seed; provider parameter differences are recorded. Repetitions are explicit, but deterministic settings and model identifiers do not guarantee deterministic results. Provider cache effects may remain; cached tokens are recorded if provided. Outputs retain raw and reference-validated answers. A reference-valid citation only means that its number/page matches supplied context; it does **not** establish claim support. An exact abstention marker is a format observation, not proof the abstention was correct. Truncation and empty model responses require human review.

The reviewer should inspect the source pages and expected answer, then label correctness and abstention correctness separately. Split each response into factual claims and annotate whether each is supported and whether its citation actually supports it; record ambiguous cases and resolve disagreements with an independent reviewer. Report each numerator and denominator, errors, missing usage, and no-evidence cases. Compare paired cases only; report p50/p95 per model as generation latency and keep retrieval latency separate. The end-to-end report also gives a composed retrieval-plus-generation latency; retrieval is measured once and reused, so this is not a directly timed end-to-end request. Avoid lexical-overlap-only scoring, broad unsupported generalizations and model rankings without reviewed live data. The report deliberately leaves human judgments null until imported, and missing billing data is not zero.

Security and spending: no provider request is sent in mock or dry-run mode. Live mode requires explicit approval flags and checks for keys only in the process environment. Requests use no application retry or fallback; timeouts remain potentially billable. A durable journal reserves estimated cost and request count before each dispatch and refuses to replay ambiguous attempts. Estimated reservations are based on assumptions, not a hard billing guarantee. For every future run, verify prices, provider privacy terms and account quotas; consult `LIVE_MODEL_EVALUATION.md` for exact commands and limitations.

The independent follow-up audit in `MODEL_BENCHMARK_AUDIT.md` found that v1's cases labeled contradictory compare separate entities, and identified page/label ambiguities without modifying held-out data. The separate 12-case development pilot adds an actual same-subject contradiction. Use `BLINDED_REVIEW_RUBRIC.md` and the blinding utility before any human model comparison; the runner's raw review template exposes model identity.
